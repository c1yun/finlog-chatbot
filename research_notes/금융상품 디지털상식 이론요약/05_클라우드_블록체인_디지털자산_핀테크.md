## KQ1. 클라우드 컴퓨팅 (IaaS/PaaS/SaaS, 배포모델, 가상화·컨테이너, 서버리스, MSA, API, CDN·엣지, 금융권 클라우드 규제·활용)

### Takeaway
IaaS/PaaS/SaaS는 "누가 어디까지 관리하느냐(책임 범위)"로 구분하며, 복기상 4개 회차 반복 출제된 최빈출 축이다. 금융권은 전자금융감독규정 제14조의2(2019.1.1 개정 시행)에 따라 중요도 평가 → CSP 안전성 평가(금융보안원) → 업무위수탁 보고 절차를 거쳐 클라우드를 이용하며, 2026년에는 SaaS가 망분리 예외로 명시되어(4~5월 시행) 혁신금융서비스 심사 없이 내부망에서 사용 가능해졌다.

### Cited Findings
**(1) 금융권 클라우드 이용 절차·규정**
- 전자금융감독규정 제14조의2는 8개 항으로 구성되며, 금융보안원이 2025년 5월 발간한 「금융분야 클라우드컴퓨팅서비스 이용 가이드」가 7단계 절차를 체크리스트로 안내 — [AWS 기술 블로그: 금융 클라우드 가이드 A to Z part1](https://aws.amazon.com/ko/blogs/tech/financial-cloud-guide-a-to-z-part1/)
- 2019.1.1 시행 개정으로 금융권 클라우드 이용 범위가 개인신용정보·고유식별정보까지 확대되고, 금융권 전용 안전성 기준(별표 2의2)이 처음 마련됨. 금융회사가 자체 정보자산 중요도 평가 기준으로 "비중요 정보처리시스템"을 지정 가능 — [금융위원회 보도자료 73442](https://fsc.go.kr/no010101/73442)
- 금융보안원 CSP 안전성 평가 항목은 기존 141개 → 54개(필수 16·대체 38)로 간소화된 것으로 보도(시점·현행 여부 확인 필요) — [it-server-room 금융보안원 CSP 안전성평가 정리](https://www.it-server-room.com/%ea%b8%88%ec%9c%b5%eb%b3%b4%ec%95%88%ec%9b%90-csp-%ec%95%88%ec%a0%84%ec%84%b1%ed%8f%89%ea%b0%80-%ed%81%b4%eb%9d%bc%ec%9a%b0%eb%93%9c-cloud-%eb%8f%84%ec%9e%85-%ed%95%84%ec%88%98%ec%a0%88%ec%b0%a8/)
- 금융보안원 가이드는 권고 성격이며 법규와 충돌 시 법규 우선 — [AWS 기술 블로그 동일 글](https://aws.amazon.com/ko/blogs/tech/financial-cloud-guide-a-to-z-part1/)
- 2026.1.19 금융위·금감원, 내부 업무망에서 클라우드 SaaS 사용 시 보안요건 충족하면 망분리 예외(고유식별정보·개인신용정보 처리 시 제외)로 하는 전자금융감독규정 시행세칙 개정안 사전예고 — [쿠키뉴스 2026.1.19](https://www.kukinews.com/article/view/kuk202601190057)
- 위 세칙 개정 시행 후 혁신금융서비스 심사 없이 SaaS 이용 가능(2024.8 로드맵 1단계의 제도화). 시행일은 내부 노트가 "2026.4.20"으로 적고(비즈워치 5/22 인용), 법률 뉴스레터 제목은 "2026년 5월경 시행"으로 표시 → 정확한 시행일 (확인 필요) — [비즈워치 2026.5.22](https://news.bizwatch.co.kr/article/finance/2026/05/22/0043); [세종 뉴스레터 3267](https://www.shinkim.com/kor/media/newsletter/pdf/3267)

**(3) 개념 정리 — 표준 개념(교과·용어사전 수준, URL 미확보)**

| 구분 | 정의 | 사용자가 관리 | 제공자가 관리 | 대표 예시 |
|---|---|---|---|---|
| IaaS (Infrastructure as a Service) | 서버·스토리지·네트워크 등 컴퓨팅 인프라를 가상화해 제공 | OS, 미들웨어, 런타임, 데이터, 애플리케이션 | 서버·스토리지·네트워크·가상화 | AWS EC2/S3, MS Azure VM, Google Compute Engine, 네이버클라우드 |
| PaaS (Platform as a Service) | 애플리케이션 개발·실행 플랫폼(OS·런타임·DB 포함) 제공 | 데이터, 애플리케이션 | 인프라 + OS·미들웨어·런타임 | Heroku, Google App Engine, AWS Elastic Beanstalk, Azure App Service |
| SaaS (Software as a Service) | 완성된 소프트웨어를 인터넷으로 구독 이용 | 사용자 설정·데이터 입력 정도 | 전부(앱까지) | MS 365, Salesforce, Google Workspace, Slack, Zoom |
| (참고) FaaS/서버리스 | 함수 단위 코드만 올리고 실행 시에만 과금, 서버 관리 불필요 | 함수 코드 | 실행환경·스케일링 전부 | AWS Lambda, Azure Functions, Google Cloud Functions |
| (참고) BaaS(금융) | Banking as a Service: 은행 기능을 API로 비금융사에 제공(임베디드 금융의 기반) | — | — | 아래 KQ7 참조 |

- 책임 범위 암기: "온프레미스(전부 사용자) → IaaS(인프라까지 제공자) → PaaS(플랫폼까지) → SaaS(앱까지)". 추상화 수준이 올라갈수록 사용자의 통제권은 줄고 편의성은 커짐.
- 클라우드 보안 공동책임 모델(Shared Responsibility Model, 표준 개념): CSP는 "클라우드 자체의 보안(of the cloud: 물리 시설·하드웨어·가상화 계층)", 이용자는 "클라우드 안에서의 보안(in the cloud: 데이터, 접근권한, 암호화, OS 패치 등)"을 책임. IaaS일수록 이용자 책임이 크고 SaaS일수록 작음.

| 배포 모델 | 정의 | 특징 |
|---|---|---|
| 퍼블릭 클라우드 | CSP가 다수 고객에게 공유 인프라 제공 | 저비용·탄력적, 멀티테넌시 |
| 프라이빗 클라우드 | 단일 조직 전용 클라우드(자체 구축 또는 전용 호스팅) | 보안·통제 유리, 비용↑ |
| 하이브리드 클라우드 | 퍼블릭+프라이빗(또는 온프레미스) 연계 운영 | 민감 데이터는 내부, 탄력 워크로드는 외부 |
| 멀티 클라우드 | 2개 이상 CSP 동시 이용(AWS+Azure 등) | 종속(lock-in) 회피, 장애 분산 |
| 온프레미스 | 자체 전산실에 서버 보유·운영 | 초기 투자(CAPEX) 큼, 전통 금융권 기본 형태 |

| 비교 | 가상머신(VM) | 컨테이너 |
|---|---|---|
| 핵심 | 하이퍼바이저 위에 게스트 OS를 통째로 올림 | 호스트 OS 커널을 공유, 앱+라이브러리만 격리 |
| 무게·기동 | 무겁고 느림(GB, 분) | 가볍고 빠름(MB, 초) |
| 격리 수준 | 강함(OS 단위) | 상대적으로 약함(프로세스 단위) |
| 대표 기술 | VMware, KVM, Hyper-V(하이퍼바이저 Type1=베어메탈, Type2=호스트형) | 도커(Docker) — 이미지·컨테이너; 쿠버네티스(Kubernetes, K8s) — 다수 컨테이너의 배포·확장·복구 자동화(오케스트레이션) |

| 비교 | 모놀리식 | MSA(마이크로서비스 아키텍처) |
|---|---|---|
| 구조 | 하나의 큰 애플리케이션 | 작은 독립 서비스들이 API로 통신 |
| 배포 | 전체 재배포 | 서비스별 독립 배포·확장 |
| 장단점 | 단순·초기 개발 빠름 / 변경·확장 어려움 | 민첩·장애 격리 / 운영 복잡도·분산 트랜잭션 난이도 |

- API(Application Programming Interface): 프로그램 간 기능·데이터를 주고받는 규약. REST API: HTTP 메서드(GET/POST/PUT/DELETE)와 URI로 자원을 표현하는 아키텍처 스타일, 주로 JSON. 오픈 API: 외부 개발자에게 공개한 API(오픈뱅킹 공동 API가 금융권 대표 사례). 웹훅(Webhook): 클라이언트가 반복 조회(polling)하는 대신 이벤트 발생 시 서버가 지정 URL로 데이터를 "밀어주는(push)" 방식 — 표준 개념.
- CDN(Content Delivery Network): 전 세계 분산 캐시 서버(엣지 서버)에 콘텐츠 복제, 사용자 가까운 곳에서 응답(지연↓, 원서버 부하↓). 엣지 컴퓨팅: 데이터 발생 지점(단말·현장) 근처에서 처리해 지연·대역폭을 줄이는 방식, 중앙집중식 클라우드와 보완 관계 — 표준 개념.
- CSAP(클라우드 보안인증, Cloud Security Assurance Program): 공공기관이 이용하는 민간 클라우드 서비스에 대해 KISA가 보안 기준 충족 여부를 평가·인증하는 제도(과기정통부 고시). 2023년부터 상·중·하 등급제 도입 — 표준 개념(세부 등급 요건·2026 현행 개정 사항은 확인 필요). 금융권은 CSAP가 아니라 전자금융감독규정 기반 "금융보안원 CSP 안전성 평가"를 사용한다는 점이 구분 포인트(출처: 위 금융위 73442, AWS 블로그).

### Inferences

## KQ2. 망분리 규제 완화 로드맵·디지털금융안전법·물리적/논리적 망분리·제로트러스트

### Takeaway
2024.8 금융위 「금융분야 망분리 개선 로드맵」은 1단계(혁신금융서비스로 SaaS·생성형 AI 허용, 2024.12~) → 2단계(개인신용정보 처리 SaaS, 연구개발망 등 추가 완화) → 3단계(자율보안·결과책임 체계 전환)로 설계됐고, 2026년에는 SaaS 예외의 규정화(1월 사전예고→4~5월 시행), 보안 목적 AI 활용 한시 완화(5.24 발표, 49개사 대상·1년), 7.10 금융위원장의 "AI·보안 역량 충분한 금융회사 망분리 전면 해제 방안 조속 발표" 발언까지 진행됐다. 2026.10.14 현재 전면 해제의 확정 공식 발표는 검색에서 확인되지 않았고, 디지털금융안전법은 제정 "추진·검토" 단계(국회 제출 여부 확인 필요)다.

## KQ3. 블록체인 (DLT, 블록 구조, 합의 알고리즘, 스마트계약, 퍼블릭/프라이빗/컨소시엄, 포크, 레이어, 지갑, 트릴레마)

### Takeaway
복기 키워드 "블록체인 특징", "퍼블릭·프라이빗 블록체인"(2개 회차)이 확인되는 출제 축이며, 이번 조사에서는 토큰증권 법의 "분산원장" 법적 정의(금융위, 2026.1)가 유일하게 1차 출처로 확보됐다. 나머지는 표준 개념으로 비교표를 정리했다.

### Cited Findings

- 모바일 주민등록증에 블록체인·암호화 등 보안기술 적용(행안부 보도자료 전재) — [금융위 게시 84152](https://www.fsc.go.kr/po010103/84152?curPage=50)
- KB국민은행 블록체인 기반 디지털 채권 발행 사례(KBW 2026) — [딜사이트 KBW 2026](https://dealsite.co.kr/articles/169897)
- 한국은행 프로젝트 한강: "블록체인 기반 기관용(도매) CBDC"를 한은이 발행, 은행이 예금토큰 발행 — [헤럴드경제 2026.7.19](https://www.heraldk.com/article/2026071917255421848)

**개념 정리 — 표준 개념(URL 미확보)**
- 블록체인: 거래 기록(블록)을 해시로 연결(체인)하여 네트워크 참여자(노드)가 분산 저장·검증하는 분산원장(DLT). 특징 = 탈중앙화, 불변성(위·변조 곤란), 투명성, 가용성(단일 장애점 없음), 익명성(가명성).
- 블록 구조: 블록 헤더(이전 블록 해시, 머클루트, 타임스탬프, 난이도, 논스) + 블록 바디(거래 목록). 해시 = 임의 길이 입력을 고정 길이 출력으로 바꾸는 일방향 함수(SHA-256). 머클트리 = 거래들을 쌍으로 해시해 올라가 하나의 머클루트로 요약, 특정 거래 포함 여부를 효율 검증. 논스(nonce) = PoW에서 목표 난이도 이하 해시를 찾기 위해 바꿔 넣는 임의 값(채굴 = 이 값을 찾는 과정).

| 합의 알고리즘 | 원리 | 장점 | 단점 | 대표 |
|---|---|---|---|---|
| PoW(작업증명) | 연산(해시 퍼즐) 먼저 푼 노드가 블록 생성 | 보안성 검증됨 | 전력 소모, 느림(비트코인 약 10분) | 비트코인 |
| PoS(지분증명) | 보유 지분(스테이킹)에 비례해 검증자 선정 | 에너지 효율, 빠름 | 부익부 우려, 'Nothing at stake' | 이더리움(2022.9 '더 머지'로 PoW→PoS 전환) |
| DPoS(위임지분증명) | 토큰 보유자가 투표로 소수 대표 노드 선출 | 매우 빠름 | 중앙화 우려 | EOS, 트론 |
| PBFT(실용적 비잔틴 장애 허용) | 허가된 노드 간 다단계 투표, 전체의 2/3 초과 동의 시 확정(악의 노드 1/3 미만 허용) | 즉시 최종성, 포크 없음 | 노드 수 많으면 통신량 급증 → 프라이빗·컨소시엄에 적합 | 하이퍼레저 패브릭 계열 |

| 구분 | 퍼블릭 블록체인 | 프라이빗 블록체인 | 컨소시엄(연합형) 블록체인 |
|---|---|---|---|
| 참여 | 누구나(비허가형) | 단일 기관 허가 노드만 | 복수 기관이 공동 운영(허가형) |
| 합의 | PoW/PoS | 기관 내부 규칙·PBFT | PBFT 등 |
| 속도·확장성 | 낮음 | 높음 | 높음 |
| 탈중앙성 | 높음 | 낮음 | 중간 |
| 암호화폐 | 보통 필요(인센티브) | 불필요 | 불필요 |
| 예시 | 비트코인, 이더리움 | 기업 내부 원장 | 하이퍼레저 패브릭(리눅스재단), R3 코다, 금융권 공동 인증(과거 뱅크사인) |

- 스마트 계약(Smart Contract): 조건 충족 시 자동 실행되는 블록체인상 프로그램(닉 사보 개념, 이더리움이 구현). 이더리움 스마트계약 언어 = 솔리디티(Solidity), 실행 환경 = EVM, 실행 수수료 = 가스(Gas). ERC-20(대체 가능 토큰 표준), ERC-721(NFT 표준).
- 노드·채굴·반감기: 풀 노드는 전체 원장을 보관·검증. 비트코인 채굴 보상은 약 4년(21만 블록)마다 절반으로 감소(반감기): 50→25→12.5→6.25→3.125 BTC(2024.4 4차 반감기), 총 발행 한도 2,100만 개.
- 51% 공격: 네트워크 해시파워(또는 지분)의 과반을 확보한 주체가 거래 이력을 되돌리거나 이중지불을 시도하는 공격(퍼블릭 PoW 소형 체인에 취약).
- 하드포크 vs 소프트포크: 하드포크 = 이전 버전과 호환되지 않는 규칙 변경, 체인이 둘로 갈라질 수 있음(비트코인→비트코인캐시 2017, 이더리움→이더리움클래식 2016). 소프트포크 = 하위 호환되는 규칙 강화(세그윗 2017).
- 레이어1 vs 레이어2: L1 = 기본 체인(비트코인·이더리움 메인넷), L2 = L1 위에서 처리량·수수료 문제를 해결하는 확장 솔루션(라이트닝 네트워크, 롤업·아비트럼·옵티미즘, 폴리곤).
- 지갑: 공개키(주소 생성·공개)/개인키(서명·절대 비공개), 핫월렛(인터넷 연결, 편의성↑ 해킹 위험↑) vs 콜드월렛(오프라인 보관, 하드웨어·종이 지갑) — 가상자산이용자보호법이 이용자 자산 80% 이상을 콜드월렛 보관하도록 한 근거 개념(KQ5 참조).
- 블록체인 트릴레마(비탈릭 부테린): 탈중앙화(Decentralization)·보안성(Security)·확장성(Scalability) 셋을 동시에 달성하기 어렵다는 명제 → L2·샤딩이 확장성 대응.
